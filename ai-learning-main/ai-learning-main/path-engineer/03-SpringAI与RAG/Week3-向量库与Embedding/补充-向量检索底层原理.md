# 补充 · 向量检索底层原理

> ⏱️ 阅读：30 分钟
> 🎯 目标：搞清楚 Spring AI + Milvus 一行 `similaritySearch()` 背后到底发生了什么，以及查询效率是怎么保证的
> 📌 前置：已完成 Day1（Embedding 原理）、Day2（Milvus 部署）

---

## 0. 心法

> **RAG 的检索不是按文本检索的，是按"向量几何位置"检索的。**
> `content` 字段只是被"顺便带回来"的副产品，**它根本不参与匹配**。

这是初学者最容易踩的认知坑。把这句话刻在脑子里，下面的内容才会顺。

---

## 1. 完整调用链（顶层视角）

你写的代码：

```java
List<Document> docs = vectorStore.similaritySearch(
    SearchRequest.query("什么是 RAG")
        .withTopK(3)
        .withSimilarityThreshold(0.7)
        .withFilterExpression("category == 'rag'")
        .build()
);
```

底层发生了 6 步：

```
similaritySearch("什么是 RAG")
        │
        ▼
[1] EmbeddingModel.embed("什么是 RAG")
        │   调通义/OpenAI 的 Embedding 接口
        ↓ 返回 float[1024]
[2] FilterExpressionConverter.convert(...)
        │   Spring AI 把通用过滤表达式翻译成 Milvus 表达式
        ↓
[3] MilvusServiceClient.search(SearchParam{
        collectionName  = "helloai_docs",
        vectorFieldName = "embedding",
        vectors         = [queryVec],
        topK            = 3,
        metricType      = COSINE,
        expr            = "metadata['category'] == 'rag'",
        outFields       = ["doc_id","content","metadata"]
    })
        ↓ gRPC
[4] Milvus 服务端：
        Proxy → QueryNode（HNSW 检索 + 标量过滤）→ 返回 topK
        ↓
[5] 解包成 List<Document>（含 content + score + metadata）
        ↓
[6] 按 similarityThreshold 过滤掉分数低的
        ↓
返回给你
```

**关键认知**：第 [4] 步 Milvus 内部根本不读 `content` 字段。`content` 是在第 [4] 步末尾"按主键回表"时才被读出来的。

```
       └─────────────────────────────┘
```

## 3. HNSW 算法直觉（查询效率核心）

### 3.1 为什么不能暴力查（FLAT）

```
for each 向量 in 全表：
    计算 cosine(query_vec, doc_vec)
排序 → 取 topK
```

百万条 × 1024 维 = 每次查询 10 亿次浮点乘加，**几秒一次，无法生产用**。

### 3.2 HNSW 的多层图思想

把所有向量构建成一个**多层图**：

```
Layer 2:  ●─────────●         （稀疏层，全局跳跃用）
            │       │
Layer 1:  ●─●───●───●─●        （中等密度）
          │ │   │   │ │
Layer 0:  ●─●─●─●─●─●─●─●─●    （全部向量都在，密集）
```

查询过程：

1. **从最顶层一个入口点开始**，贪心找当前层离 query 最近的点
2. **下钻到下一层**，从上一层的最近点继续贪心
3. **到第 0 层**做精细搜索，在 `ef`（探索宽度）的邻居窗口里找 topK

> 直觉类比：像在地图上找一家咖啡店——先在国家级地图（顶层）跳到大致区域，再切省级地图，最后到街道地图精确定位，**不需要扫描整张地图**。

### 3.3 复杂度对比

| 数据量 | FLAT（暴力） | HNSW |
|------:|:---:|:---:|
| 1 万   | 5 ms | 1 ms |
| 100 万 | 500 ms | 5 ms |
| 1 亿   | 50 s | 20 ms |

HNSW 的复杂度是 **O(log N)**，FLAT 是 **O(N)**。

### 3.4 三个调参旋钮（必背）

| 参数 | 时机 | 含义 | 默认 | 调大的代价 |
|------|------|------|------|------|
| `M` | 建索引 | 每个节点的邻居数 | 16 | 内存↑ 召回↑ |
| `efConstruction` | 建索引 | 建图时探索宽度 | 200 | 建索引慢↑ 质量↑ |
| `ef` | **查询时** | 查询时探索宽度 | 64 | 查询慢↑ 召回↑ |

**线上调优只调 `ef`**——它是**运行时**参数，不用重建索引。
- 召回率不够 → `ef` 调到 128 / 256
- QPS 不够 → `ef` 降到 32

### 3.5 其他索引类型对比（场景快查）

| 索引 | 一句话原理 | 速度 | 召回 | 内存 | 用在哪 |
|------|----------|:----:|:----:|:----:|------|
| **FLAT** | 暴力扫描 | 慢 | 100% | 低 | 数据量 < 1 万 |
| **IVF_FLAT** | 先聚类只查最近的桶 | 中 | 95%+ | 中 | 100 万级 |
| **HNSW** ⭐ | 多层图邻居跳跃 | **快** | 95%+ | **高** | **生产首选** |
| **IVF_PQ** | IVF + 量化压缩 | 快 | 90% | 低 | 上亿条但内存紧 |

## 4. content 字段是怎么"取回"的（最后一公里）

第 0 层图遍历找到 topK 个**主键 ID** 后，Milvus 还要做一步：

```
按主键 ID 去存储里把 content / metadata 字段读出来
```

这一步的效率取决于：

1. **集合是否 Load 到内存**（`loadCollection`）
   不 load 要从 MinIO / S3 拉，慢 10-100 倍
2. **outFields 字段大小**
   `content` 越长，序列化和网络传输越慢
3. **是否启用 mmap**
   大 content 字段建议开 mmap，节省内存

## 5. 查询效率的 6 大保障机制（系统全景）

```
┌─────────────────────────────────────────────────────┐
│ 保障层级           什么发挥作用              提速量级 │
├─────────────────────────────────────────────────────┤
│ ① 向量索引(HNSW)   O(log N) 替代 O(N)           100x │
│ ② 标量预过滤+索引  Filter 先剪枝再算向量         2-10x│
│ ③ Partition 分区   只在子集里查                N/分区数│
│ ④ Load 到内存     避免磁盘 IO                10-100x│
│ ⑤ Segment 并行     QueryNode 多 segment 并发    ~核数 │
│ ⑥ 客户端缓存       同 query 直接命中               ∞  │
└─────────────────────────────────────────────────────┘
```

### 5.1 HNSW 索引（已讲）

### 5.2 标量预过滤 + 标量索引 ⭐

当你写 Filter：
```
metadata['tenant'] == 'fletcher'
```

Milvus 的执行计划：

```
先用 Filter 把不符合的剪掉 → 剩下的子集再走 HNSW 找 topK
```

**注意点**：

- Filter 命中率高（剪掉很多）→ 候选集小，HNSW 自动退化为暴力扫描，反而 OK
- Filter 命中率低（剩 99% 数据）→ 等于没过滤，还多一次比较开销
- **经常过滤的标量字段要建标量索引**（如 `STL_SORT` 或 `INVERTED`），否则 Filter 是全表扫

### 5.3 Partition（分区）

按"租户 / 时间 / 业务线"把数据分到不同 partition，查询时指定 partition：

```
只在 partition_fletcher 里查 → 跳过其他所有数据
```

**使用门槛**：
- 百万级以下 → 不需要
- 亿级 + 多租户 / 多时间窗 → 强烈推荐

### 5.4 Load 到内存（最重要的运维点）

不 load → 数据在 MinIO / S3 → 每次查询都要拉 → 慢死。

- Spring AI 自动建表时会自动 load
- **重启 Milvus 后要重新 load**（社区版默认不持久化 load 状态）

### 5.5 Segment 并行查询

Milvus 写入数据时按 1 GB 切 Segment，查询时**所有 Segment 并行查**，最后合并 topK。
这是 Milvus 比 FAISS 强的地方——天然支持并行。

### 5.6 客户端缓存（应用层）

Spring AI 不带缓存，但 RAG 应用可以自己包一层：
- FAQ 类的固定问题特别有效
- 缓存 key = query 文本（或 query 向量的 hash） + topK + filter

## 6. 性能调优 Cheat Sheet

### 按数据量定调优强度

| 数据量 | 你需要做什么 |
|--------|-------------|
| **< 1 万** | 啥都不用动，HNSW 默认参数无脑用 |
| **1 万 – 100 万** | 确认 collection 已 load；`ef=64` |
| **100 万 – 1000 万** | 标量字段建索引；`ef=128`；考虑 partition |
| **1000 万+** | 用 Cluster 版；考虑 PQ 量化；冷热分离 |

### 通用最佳实践（写代码时养成习惯）

| 场景 | 怎么做 | 为什么 |
|------|--------|--------|
| 多租户 / 多文档库 | metadata 过滤 | 缩小候选集 |
| 怕检索到不相关内容 | `similarityThreshold = 0.7~0.8`（COSINE） | 卡掉低分结果 |
| topK 选多少 | 3-5 够用，别超 10 | 多了反而上下文污染 |
| 向量归一化 | Spring AI 自动做 | COSINE 度量必须 |

## 7. 三问总结

| 问题 | 答 |
|------|----|
| **底层逻辑是什么？** | 问题 embed 成向量 → 向量索引里找几何最近的 topK → 按主键回表取 content |
| **content 怎么检索的？** | **不是按 content 文本检索**，content 只是查到向量后顺带返回的字段 |
| **查询效率怎么保证？** | HNSW O(log N) + 标量预过滤 + Load 内存 + Segment 并行，单查询稳定毫秒级 |
